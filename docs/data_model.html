churn — data model

Every table in this model exists to protect one sentence: a person who uses coupons, cashback, or both is counted once, in the quarter their behaviour happened. The design problem is not the churn arithmetic — it is that the same human arrives through two systems under two identities, on two different date columns, with a payment workflow that decides weeks later whether one of those arrivals ever happened.

01 Conceptual model

Six business concepts, before any table exists. Everything physical downstream is a consequence of how these six relate.

Solid edges are identifying relationships resolved by the Identity Map. Dashed edges are assignments computed in SQL, not stored keys. Merchant is carried on both event entities but is deliberately not modelled as a dimension — see decision D5.

Why the Person / Source Identity split is the whole model

Across 2025, activity arrives under 111 distinct source identities — 53 coupon-side and 58 mapped cashback-side. They belong to 66 people. 44 of those 66 were active on both channels at some point in the year, and in every single quarter exactly 4 people are active on both sides at once — the same four, U057–U060, all four quarters.

Aggregate on the source id and 2025's active base reads 111 instead of 66 — a 68% overstatement, and a churn rate computed on a base that double-counts its most engaged users. Every layer below resolves identity before anything is counted, which is why the identity map is joined in the intermediate layer and never later.

Concept definitions

ConceptDefinitionWhy it is modelled this way
Person One human being, keyed by unified_user_id. 66 exist. The financial model counts people, not accounts. Making this the fact grain means "counted once" is enforced by the primary key rather than by a DISTINCT someone might forget.
Source Identity A person as one source system knows them: (coupon, C1055), (cashback, B2055). Kept as its own concept rather than as two columns on Person, so a third channel (app, referral) is a new row, not a schema migration.
Coupon Event A coupon copy action, dated by event_date. Activity is instantaneous and self-evidencing: once it happens it never changes state. This is why coupons need no maturity handling at all.
Cashback Transaction A purchase, dated by purchase_date, carrying a status that is decided later. Behaviour and its confirmation are separated in time. The model keeps them separate too: purchase_date dates the behaviour, status_updated_date only ever describes the paperwork.
Affiliate Source One of six networks feeding cashback transactions. Not a dimension table — six values with no attributes. Modelled as a degenerate attribute on the transaction, and profiled per source in the quality layer, which is where it actually matters.
Quarter A calendar quarter of 2025, the analysis period. The only conformed dimension. Materialised as a table rather than computed inline, because inactivity needs a row to exist against, and a derived quarter cannot produce one.

02 The grain contract

One sentence that every downstream number depends on, and the three properties that make it hold.

Grain

fct_user_quarter_activity =
one row per (unified_user_id, quarter_label) — 66 × 4 = 264 rows, always

Property 1 — dense, not sparse

The table is built from a spine: every person crossed with every quarter, then left-joined to activity. A person with no activity in Q3 still occupies a Q3 row carrying is_active = FALSE.

This is the single most consequential physical choice in the model. Churn is a statement about absence, and absence cannot be aggregated if it is represented by a missing row. With a sparse table every downstream query needs an outer join against a generated calendar and gets it subtly wrong — COUNT(*) silently becomes "quarters with data" instead of "quarters". Densifying once, at the fact layer, means every mart above it is a plain COUNTIF.

Property 2 — the definition is a dimension, not a fork

The brief requires two answers: activity counting pending cashback, and activity counting only approved. The fact table stores both flags on the same row (is_active_baseline, is_active_approved_only), and v_user_quarter_active unpivots them into a definition_name column.

The alternative — a second pipeline for the sensitivity analysis — is how two numbers drift apart six months later when someone fixes a bug in one copy. Here, every mart computes both definitions in the same query, from the same rows, so they cannot disagree except where the rule genuinely differs. The whole sensitivity analysis reduces to GROUP BY definition_name.

Property 3 — the person is the unit, the channel is an attribute

A person active on both coupons and cashback in the same quarter produces one row with activity_mix = 'both'. The channel breakdown survives as attributes (is_active_coupon, is_active_cashback, activity_mix) so channel analysis is still possible — but it is impossible to accidentally count that person twice, because there is no second row to count.

03 Layers & lineage

Five processing layers plus a cross-cutting quality layer. Each layer is allowed to do exactly one kind of work, so that when a number is wrong there is only one place it can be wrong.

L0 landing L1 staging L2 unified L3 fact L4 marts & dims Quality (cross-cutting)

Marts for source profiling, approval maturity and the as-of restatement read from the staging and fact layers as well; they are omitted from the drawing to keep the spine legible and are fully specified in the catalog below.

What each layer is allowed to do

LayerPermitted workForbiddenWhy the boundary
L0 raw Land bytes as extracted. Type only where unambiguous. Any cleaning, filtering or renaming. Raw is the evidence. If it is cleaned on the way in, a disputed number can never be traced back to what the source actually sent.
L1 staging Trim, case-normalise, de-duplicate to the business key, classify status vocabulary. Joining across sources; dropping rows. De-duplication must happen before any join, or a duplicate id fans out into duplicated activity. Nothing is dropped so the quality layer can still count what was wrong.
L2 unified Resolve identity, assign quarter, union channels, set activity flags. Aggregating. This is the only layer that knows both channels exist. Keeping it at event grain means the "counted once" rule is applied once, at a single join.
L3 fact Densify against the spine and aggregate to person × quarter. Business interpretation beyond the two definitions. Every reporting question in the brief is answerable from this one table. If a mart needs to go back to events, the fact table is missing a column.
L4 marts Window functions, cohort pivots, ratios, presentation shape. Re-deriving activity. Marts must be cheap and obviously correct. A mart that recomputes eligibility is a second definition waiting to drift.
Quality Count defects; assert reconciliation identities across layers. Fixing anything. A layer that both detects and silently repairs defects will eventually hide one. Detection and remediation stay separate jobs.

06 Design decisions

Seven choices where a defensible alternative existed. Each records what was chosen, why, and what was rejected.

D1 · Dense spine instead of a sparse activity table

The fact table materialises every person × quarter combination, active or not. It makes churn a COUNTIF and makes LEAD() safe across gaps.

Rejected: aggregating only observed activity. On a sparse table LEAD() skips silent quarters and jumps to the next active one — reporting near-perfect retention for users who disappeared for six months. The bug is invisible in review and catastrophic in a model.

D2 · Churn definition as a dimension, not a fork

Both definitions are computed on every row of every mart, distinguished by definition_name.

Rejected: a parameterised pipeline rebuilt per definition, or a second copy of the SQL. Both make the sensitivity analysis a diff between two runs rather than a column, and both drift the moment one copy is fixed and the other is not.

D3 · Flag rows, never drop them

Staging and the unified layer filter nothing. Bad rows carry is_in_scope = FALSE and a reason; the fact layer applies the filter, the quality layer counts what was filtered.

Rejected: WHERE status != 'rejected' in staging. It produces the same numbers and destroys the ability to answer "how many did we exclude, and which ones" — the first question asked when a churn figure is challenged.

D4 · Unmapped identities excluded and reported, not invented

B9999 has no identity-map row. Its transaction is excluded from the fact table, raised as an error, and listed row-by-row.

Rejected — synthesising a unified id from the source id: puts a fabricated person in the denominator and hides a broken identity feed behind a plausible number.
Rejected — dropping it silently: the same distortion with no trace at all. Excluding loudly is the only option that keeps the number defensible and gets the feed fixed.

D5 · Merchant is a degenerate attribute, not a dimension

merchant_id is carried on the event stream for drill-down and never joined to anything.

Rejected: a dim_merchant. There are no merchant attributes in scope and churn is not measured per merchant, so the dimension would be a join that costs something and buys nothing. When merchant attributes arrive — category, commercial tier — it becomes a conformed dimension and the event stream already holds the key.

D6 · Periodic-snapshot fact, not an accumulating snapshot

One row per person per quarter recording state, rather than one row per person tracking their lifecycle milestones through updates.

Rejected: an accumulating snapshot with churned_at / reactivated_at columns. It requires the churn definition to be fixed at write time — and the entire brief is about comparing definitions. Snapshot rows let the definition stay a read-time decision.

D7 · Vintage restatement as a table function reading staging

tvf_user_quarter_activity_as_of takes a cutoff date and reconstructs activity as it was known then, reading staging directly.

Rejected — a snapshot table appended each reporting run: correct, but it only starts producing evidence from the day it is switched on, and the reporting-lag decision is needed now. Deriving vintages from status_updated_date reconstructs history that already exists. In production both belong: the TVF to choose the lag, snapshots to prove it afterwards.

08 At production scale

What this model is already shaped for, and the three places it would change.

Already in place

Staging tables are partitioned on activity month and clustered on their join keys; the fact table is clustered on unified_user_id. At 264 rows this buys nothing — it is declared for shape, so the model does not need restructuring the first time it meets real volume. Every build statement is CREATE OR REPLACE and therefore idempotent: the pipeline can be re-run at any point without a cleanup step.

Full refresh → incremental

Today every layer rebuilds completely. At scale, staging and the event stream become incremental on activity month, with a rolling reprocess window wide enough to absorb late-arriving affiliate data — the decisions_landing_in_later_quarter and max_days_to_decision columns already measure how wide that window needs to be. The fact table stays a full rebuild of the current and prior quarter: it is small by construction, being bounded by people × quarters rather than by events.

Identity becomes slowly-changing

The identity map is treated as current-state here. In production, merges happen — two accounts discovered to be the same person, retroactively. That makes it a type-2 dimension with validity ranges, and raises a real question the model would then have to answer explicitly: does a merge restate history, or apply only from the merge date forward? The current design deliberately does not pretend to answer it.

Assertions become gates

dq_check_results is a table today; in Dataform the same logic becomes assertions attached to each model, and publication is blocked on COUNTIF(check_status = 'FAIL' AND severity = 'error') = 0. The reconciliation identities matter most here — they are the checks that catch a bad refactor rather than bad data.
